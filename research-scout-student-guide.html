1. What you will build

You will build a research agent. It is one Python file, and you will write it by giving instructions to OpenCode Zen.

You give the agent a research question. The agent then decides what to search for, searches the web, reads pages, decides whether it has enough information, and writes a short research brief with sources.

You will use your own research question, not an example question. At the end of the session you will have a working program you can use again.

2. What you will be able to do by the end

1. Explain how your agent decides what to do next. You will be able to look at your own code and say why the agent chose one action instead of another.

2. Decide how much freedom your agent should have. You will weigh what you gain by letting it act on its own against what happens when it gets something wrong, decide what it may do unsupervised, and change your code so that it matches your decision.

3. Read what your agent actually did. You will read your own trace and say which pages it opened, which it only listed, and whether the report it wrote is supported by what it read.

3. Words used in this session

Keep this section open. You do not need to memorise these words. Look them up when you need them.

The seven parts of an agent

Part What it means
Model The part that decides what to do next.
Goal The research question you gave it.
Tools The actions the agent is allowed to take.
State The record of every step so far in this run. The model has no memory of its own, so your program sends the whole record back on every step.
Loop The code that asks the model, acts, looks at the result, and asks again.
Stop condition The rule that ends the run, whether the agent has finished or not.
Evaluation How you check whether the agent behaved the way you wanted.

Your three tools

Tool What it does
search_web(query) Searches the web and returns a list of results.
read_webpage(url) Opens one web page and returns the text on it.
finish(report) Ends the run and writes the research brief.

If an action is not in this list, your agent cannot take it. Adding a new capability later means adding a new tool.

Two more words you will hear

Observation. The result that comes back after the agent uses a tool. If the agent searches, the observation is the list of search results.

Trace. The printed record of everything the agent did, step by step. You will read your own trace several times.

The loop has a name: ReAct

The loop you are building comes from a 2022 research paper. The name joins two words, reason and act, and the cycle has three steps:

  1. Reason about what you still need to know
  2. Act by using one of your tools
  3. Observe the result your tool sends back

Then repeat, until you have enough evidence to answer.

Almost every AI agent framework you will meet later is built on this shape, so it is worth searching for the term afterwards. The paper is Yao et al. (2022), ReAct: Synergizing Reasoning and Acting in Language Models, at arxiv.org/abs/2210.03629.

The two questions

Ask these about any task you might hand to an AI.

  1. What is the benefit of letting the AI do this on its own? This tells you what you gain.
  2. What is the worst thing that happens if it gets this wrong? This decides how much freedom it should have.

The second question is the one that decides. Knowing the benefit alone never tells you how much freedom to give something.

2. Answer this question in one or two sentences. What do you think an AI agent is? What makes it different from a chatbot? There is no right answer. Your answer helps in planning the session.

3. Bring one research question from your own work. This choice matters more than it looks, so take a moment over it.

Your question must need information the AI model cannot already know. The model has read an enormous amount of text. If your question is about general knowledge, the model will answer it from memory, do one search to look busy, and stop. You will have built an agent and never seen it work.

Ask for something the model has no way of knowing: current prices, a recent change, specific numbers, or a comparison that needs real evidence about each option.

Examples of questions that work well:

  • What is the price of gold today, and what moved it over the past month? (This is the one used as the worked example in section 8, so you can compare your run against it.)
  • Which of three note-taking tools should our team choose for sharing meeting notes, what does each cost today, and which would you recommend?
  • What are the current entry requirements and fees for this course at three different providers?
  • How have organisations in my sector handled AI in hiring since the rules changed, and what should we do?

Examples of questions that will not work:

  • What is the capital of Malaysia? (One fact, one source.)
  • Is AI good? (Too broad to research.)
  • What is machine learning? (The model already knows this and will answer from memory.)

A quick test: if a knowledgeable colleague could answer your question well without looking anything up, the model can too, and your agent may barely run before deciding it is finished.

Please also open VS Code with OpenCode Zen once before the session and check that it responds. This takes one minute. It confirms your login is still active.

5. Your repository

Everything you produce goes into your own repository.

Create a repository called research-scout. It should end up with this structure:

research-scout/
├── research_agent.py     the program you build
├── requirements.txt      the packages your program needs
├── .env.example          the settings someone else would need, with no values
└── .gitignore            must contain the line .env

Do not put your .env file in the repository. It contains your key. Add a .gitignore file with the line .env in it before your first commit.

requirements.txt and .env.example are how someone else can run your program. Between them they say what to install and what to configure, without revealing your key. Your program is only reusable if both are there.

For work you rely on, you would also record the version of each package, for example ddgs==9.6.0 rather than ddgs. Versions change, and code that worked last month can stop working when a package updates underneath it. Names alone are enough here.

What you asked for, and what you got

You describe what you want. The model decides everything you did not mention. Those unmentioned decisions are where most of the real choices are made, and some of them matter a great deal.

Here is a real example from this program. A prompt asked only for a function that "returns a short list of search results". The model then decided, without being asked, which search service to use, how to reach it, how many results to return, what shape to return them in, and where to put the API key. One of those decisions put the key somewhere it could be read by other people. Nobody asked for that, and nobody would have noticed it without reading the code.

So it is worth naming three decisions the model made that your prompt did not ask for, and to say whether you would have made the same choice.

You can fill this in at any point once you have code to read. It is easier if you write each one down when you notice it, rather than looking for three at the end.

This is not a test of whether you used AI. You are expected to use it. It is practice in the job you will actually be doing: approving work that a machine produced and you are responsible for.

Save your terminal output

Your terminal output is what you submit, so keep it from the moment you start.

Copy everything your terminal shows after each prompt — the checkpoint test you ran and what it printed — into one plain text file. Add to the same file as you go, rather than starting a new one each time.

If you prefer to capture the final run directly, this also works:

python3 research_agent.py --eval | tee final_run.txt

If python3 is not found on your machine, try python. One of the two will work.

You can do the same thing with the buttons in the Source Control panel in VS Code, if you prefer.

6. The five prompts

Give these to OpenCode Zen one at a time, in order. After each one, check that the code does what the checkpoint says. Then commit your work and post the checkpoint number in the chat.

If the code does not work, describe the problem to OpenCode Zen in your own words. Do not paste the same prompt again.

Do not combine the prompts into one. A long prompt produces more code than you can read, and reading your own code is the main point of this session.

Prompts 1 to 4 build an agent that runs. Prompt 5 is the one that makes it research properly, and its effect is what your final run has to show.

What each prompt delivers

Prompt What it delivers
1 A program that can ask the model
2 A search tool and a page reader
3 A loop, and the state it builds up
4 Five checks that score the run
5 An agent that reads before it reports

Where the seven parts come from

Section 3 listed the seven parts every agent has. Between them, these five prompts produce all seven. When you are reading your own file and cannot find something, this table tells you which prompt made it.

Part Which prompt delivers it
Model 1
Goal 1, the question you type
Tools 2
State 3
Loop 3
Stop condition 3 sets the step limit, 5 adds the three-page rule
Evaluation 4

State is not something a prompt adds as a separate part. It is a plain Python list that the loop appends to, which is why it arrives with the loop rather than on its own.

Prompt 1 — the program

Create a beginner-friendly Python command-line program called research_agent.py.

It should ask the user for a research question and print it back.

Read three settings from a .env file: API_BASE_URL, API_KEY and MODEL. If any one of them
is missing, print which one is missing and stop. Do not guess a model name.

Call the model over plain HTTP, using the OpenAI-compatible chat completions format:

  POST to API_BASE_URL + "/chat/completions"
  Body: {"model": <MODEL>, "messages": [{"role": "user", "content": <the prompt>}]}
  The reply text is at choices[0].message.content

Send the key in an Authorization header as "Bearer <API_KEY>". Never put the key in the URL.

Send a browser-style User-Agent header. Without one the service returns 403 with error
code 1010 and refuses the request.

Give every request a timeout of 60 seconds.

When a request fails, print what actually went wrong: the error type, the message, and the
response body if there is one. Never replace an error with a generic message, and never
print the request URL.

If a request fails with 429, you are being rate limited. If the response carries a
Retry-After header, wait that long, otherwise wait two seconds. Print how long you are
waiting and why. Retry up to three times. If a request fails with a 5xx error, wait two
seconds and retry.

If the reply does not contain choices[0].message.content, print the whole response body and
stop with a clear message.

Also create a .env.example file listing the three variable names with empty values, so
someone else can see what to set without seeing my key.

Keep the program itself in one file.

Do not use LangChain, LangGraph, CrewAI or any other agent framework.

What this prompt is doing

What you ask for What it gives you
Read API_BASE_URL, API_KEY and MODEL from .env, and stop if one is missing Your settings live outside the code, so changing model later is not editing the program. And a typo in .env tells you which line is wrong instead of failing somewhere confusing.
Send the key in an Authorization header, never in the URL A key placed in the URL appears in every error message. That is the commonest way somebody publishes a working key by pasting an error into a chat.
Send a browser-style User-Agent Every program that calls a service sends a short line saying what kind of program it is. Python's marks it as a script, and the service refuses scripts before it looks at anything else.
Print the error type, the message and the response body One general message like "something went wrong" cannot tell you whether your key is wrong, the service is busy, or you asked too often. Those need three different responses from you.
When the service replies 429, wait as long as it asks 429 means you have asked too many times too quickly. Trying again straight away uses up requests that were never going to work.

Checkpoint 1: The program runs. It asks for your question and prints it back.

Prompt 2 — the tools

Add two functions to the program:

1. search_web(query) - returns up to 5 search results, each with a title, a URL and a
   snippet. Use the ddgs library (pip install ddgs). It needs no API key.
2. read_webpage(url) - fetches one page with requests, strips the HTML with
   beautifulsoup4, and returns the visible text capped at 2000 characters.

Send a browser-style User-Agent header with every page request. Many websites refuse
requests that identify themselves as a script.

Keep each one an ordinary Python function. Write a clear one-sentence description of each,
in a form an LLM could use to decide which one to call.

If a search or a page fetch fails, print the status code and the URL, and return an empty
result. Do not stop the program.

Add a way to run each function on its own from the command line so I can test them
separately.

Finally, create a requirements.txt listing every package my program needs, one per line.
List only the packages I import directly, not the packages those packages depend on.

What this prompt is doing

What you ask for What it gives you
search_web(query) and read_webpage(url) These two functions are the only ways your agent can touch the world. Anything not in this list, it cannot do.
A clear one-sentence description of each This description is what the model actually sees. It never sees the code inside your functions, so the sentence is the tool as far as it is concerned.
Page text capped at 2000 characters Web pages can be enormous. Without a cap, one page fills the whole request and there is no room for anything else.
A browser-style User-Agent on page requests Many websites refuse anything that looks like a script. Without this line your agent cannot read anything, and it will write its report from search results alone.
A requirements.txt Somebody else can install what your program needs and run it. Your instructor, reading your submission, is that somebody.

Checkpoint 2: You can run each tool on its own, using your own research question, and you get sensible results.

Prompt 3 — the loop

Turn the program into a tool-using agent with an explicit loop.

Put the step limit in a constant at the top of the file and set it to 6. Use that constant
wherever the step limit appears, including in the prompt text sent to the model. The number
the model is told must always be the number the program enforces.

On each step, send the model the goal, a description of the three tools, and everything
that has happened so far. Ask it to reply with only a JSON object, in one of these shapes:

{"reason": "one short sentence", "action": "SEARCH", "query": "..."}
{"reason": "one short sentence", "action": "READ",   "url": "..."}
{"reason": "one short sentence", "action": "FINISH", "report": "..."}

Parse that JSON. If the reply is wrapped in markdown code fences, remove them first.
If parsing still fails, print the raw reply and stop with a clear message.

Execute the chosen action. Append the action and its result to a state list, and pass the
whole state to the model on the next step.

Print the step number, the reason, the action, and a short summary of the observation.

Web page text is often full of navigation and menus. Do not assume it is clean.

When the action is FINISH, print a research brief with sections for the question, the
findings, the comparison, the recommendation, and the sources.

If the step limit runs out before FINISH, say so clearly.

A failed search, or a page that will not load, is normal. Record what happened in the state
so the model can see it on the next step, and let the agent choose again. Do not exit the
program on the first failure.

Do not use an agent framework.

What this prompt is doing

What you ask for What it gives you
An explicit loop, with the step limit in a constant The number the model is told is always the number your program enforces. Write the number by hand in two places and they drift apart the first time you change one.
A reply that is only a JSON object, in one of three shapes This is the contract between the two halves of your program. The model writes the JSON, and your code reads it. Everything else in the loop depends on that shape holding.
Append each action and its result to a state list This is where state gets built. The model remembers nothing between steps, so this list is the only memory the run has.
Remove the ``` marks a model may wrap its reply in Models often add formatting around a reply. Your program cannot read JSON with those marks still attached.
Record a failed search or an unreadable page, and carry on Pages fail to load all the time. Without this, one bad moment at step four throws away the four steps before it.

Checkpoint 3: The agent answers your question from beginning to end, and you can see every step it took.

Prompt 4 — the checks

Add an evaluation mode, run as: python research_agent.py --eval

Check five things about a completed run, and print PASS or FAIL with a total score:

1. the search tool was used at least once;
2. more than one distinct source was consulted;
3. the run stayed within the step limit;
4. the brief contains a recommendation;
5. the brief lists at least three sources.

The checks should read the run's state and output, not the model's opinion of itself.

What this prompt is doing

What you ask for What it gives you
An --eval mode with five checks A way to measure a run rather than judge it by reading it and forming an impression.
Checks that read the run's state and output A model asked to mark its own work will nearly always say it did well. These checks look at what happened instead of asking.
Check 2: more than one distinct source consulted You decide what "consulted" means. Counting the URLs listed in the brief is easier to write. Counting the pages actually opened is harder and more honest. Your choice decides what your own score is worth.
PASS or FAIL for each, and a total score A number you can compare between one run and the next, which is what makes a change measurable.

Checkpoint 4: Running python3 research_agent.py --eval prints five results and a score.

Prompt 5 — make it research properly

Run your agent at least once before you give it this prompt. Seeing what it does without these rules is what makes the rules worth having.

Improve the agent so that its report is built from pages it actually read.

1. Read more of each page.

Raise the page text limit in read_webpage from 2000 to 5000 characters.

2. Change what the model is told about FINISH.

In the tool descriptions that go into the prompt, replace the FINISH description with:

  FINISH  Write the report. Only choose this after you have read at least three
          different web pages. Base the report on the text of those pages. Search
          result titles and snippets are not enough on their own. Price tickers,
          shop pages and product listings give you a number but no explanation, so
          prefer news articles, analysis and official sources when you choose what
          to read.

3. Add a rule the model cannot talk its way past.

Before the program accepts a FINISH action, count how many different pages the agent has
read successfully.

If it is fewer than three, do not accept the report. Add a note to the state saying how
many were read, that three are required, and that it should choose READ next. Print that
FINISH was refused, then continue the loop.

If it is three or more, accept it: print the research brief and end the run.

If the report is empty, refuse it the same way and say so.

Do not let the agent read the same URL twice. If it asks for one it has already read,
refuse that too and put a note in the state.

4. Give it room to do that.

Raise the step limit constant from 6 to 8.

5. Say where each finding came from.

Ask the model to end every finding with the URL it came from, in square brackets. If a
finding comes from what the model already knew rather than from a page it read, it must
end with [no source] instead.

6. Print an honest source list.

In the research brief, replace the single Sources list with two lists, neither containing
repeats:

  Pages read    the URLs the agent opened and got text back from
  Also found    the URLs that appeared in search results but were never opened

A page that failed to load is not a source. Do not list it under either heading.

Keep everything in one file. Do not use an agent framework.

What this prompt is doing

What you ask for What it gives you
Only finish after reading three different pages This sentence goes into the tool description, so the model is told to read three pages.
The program refuses FINISH before three pages This goes into the loop, so the model cannot ignore it. Read this row against the one above: a description is a request, and a rule in your code is not.
Prefer news and analysis over price tickers and shop pages Source quality becomes part of the instruction. Without it the agent happily opens a shop page, gets a menu, and reports anyway.
End every finding with its URL, or with [no source] A reader can check a claim instead of having to trust it. This is the single change that makes your brief reviewable by someone else.
Two source lists: pages read, and links only found Your brief stops claiming sources it never opened. Before this change, a link the agent glanced at in a search result looked exactly like one it had read.

Checkpoint 5: The run reads three pages before it reports, every finding ends with a URL, and the brief prints two separate source lists.

7. How much freedom should your agent have?

By this point your agent does four things on its own. It decides what to search for. It searches without asking you. It opens web pages that nobody has checked. It decides for itself when it has enough information.

Ask these two questions about your own agent before you decide.

Question 1: What is the benefit of letting the agent do this on its own? This tells you what you gain.

Question 2: What is the worst thing that happens if it gets this wrong? This decides how much freedom it should have.

Then answer the question those two lead to: what should your agent be allowed to do on its own, and what should it have to stop and ask you about?

When no answer feels comfortable

You may find that every answer is wrong. Letting it run is too risky, and checking every step makes it useless. This is normal, and it means you are asking the right question.

When this happens, change one thing about the task until an answer becomes comfortable. You do not have to accept the task as it is. You wrote the code, so you can change it.

Here are changes you can make in ten minutes:

  • Raise the number of pages it must read before it can finish, from three to five.
  • Limit search_web to a list of websites you trust.
  • Reduce the maximum number of steps.
  • Make read_webpage open only pages that came from your own search results.
  • Add a sixth check that fails the run if any finding ends with [no source].
  • Record every step in a log file, so you can check the run afterwards.

You do not have to make any of these changes. They are here so you can see that the amount of freedom an agent has is something you set, not something the agent decides.

The lethal trifecta

Three things must not meet in the same system:

  1. Private data. It can read your files, your email, your customer records.
  2. Untrusted content. It reads web pages and documents that nobody has checked.
  3. A way to send data out. It can make a web request, call an interface, or send an email.

Any two of these are manageable. With all three, a hidden instruction inside a page it was asked to read can tell it to collect your data and send it to a stranger. The agent cannot tell that instruction apart from yours.

The agent you are building has the last two. It reads pages nobody has checked, and it can send requests out. It has no access to your private data, and the feature that would give it access — letting it read your documents or your email — is the one people ask for first.

This name is Simon Willison's, and it is worth searching for after the session.

Your agent holds the first two. It acts on its own, and it reads pages that nobody has checked. It does not yet hold the third.

Now think about the feature you will most likely want to add next: a tool that reads your email. That would give your agent the third one.

If you need to remove one of the three, the way to do it is the change you have just made. You take something away from what the agent is allowed to do on its own.

This idea has a name. It is called the lethal trifecta, and it is worth searching for after the session. It applies to every AI system you will be asked to approve at work, not only to the one you built here.

8. One real run, annotated

This trace is real. It comes from the finished agent — the one you will have after prompt 5 — on the question "what is the price of gold today, and what moved it over the past month?", captured on 18 August 2026.

What it did

STEP 1  SEARCH  "gold price today past month movement factors"  → 5 results
STEP 2  READ    tradingeconomics.com          → 5000 characters
STEP 3  READ    gold.org                      → 3256 characters
STEP 4  READ    goldprice.org                 → 0 characters   (refused)
STEP 5  READ    kitco.com                     →  867 characters
STEP 6  FINISH

Score: 5 of 5

Six steps of eight. Four pages attempted, three read. Nobody told it which ones to open.

Your run will not look like this. Nobody chose these four sites. The search returned them and the model picked from what came back, so your agent will open different pages, in a different order, even on the same question. A trace is evidence about one run. It is not a description of what a correct run looks like, and yours is not wrong for being different.

What the brief looked like

Each finding ended with the page it came from:

Gold spot price is around $4,403–$4,405 per troy ounce as of Aug 17–18, 2026
[https://www.kitco.com/charts/historicalgold.html]
[https://tradingeconomics.com/commodity/gold]

Over the past month gold has risen roughly 9.9%
[https://tradingeconomics.com/commodity/gold]

And the sources came in two lists rather than one:

Pages read:                    Also found, not opened:
  tradingeconomics.com           goldavenue.com
  gold.org                       goldprice.org
  kitco.com

Seven things worth noticing

1. One page was refused, and the agent carried on. goldprice.org returned nothing at step 4, so the agent chose a different site at step 5. Many commercial sites block programs that are not browsers. This is normal, it is not your mistake, and the run should survive it. Notice too that the refused page appears under Also found and not under Pages read, which is correct: it was never opened.

2. The agent said when a source did not have what it wanted. One finding reads: the World Gold Council "did not list a live number in the text". It read the page, did not find the figure it was looking for, and said so instead of quietly filling the gap. That sentence is worth more than the rest of the brief, because it is the agent telling you the limit of its own evidence.

3. One source is doing most of the work. Trading Economics appears in five of the six citations. The brief reads as though three sources support it. Count the brackets and you can see that one of them carries nearly all of it. Do this count on your own brief.

4. Two links are listed that nobody opened, and the brief says so. That is the honest version. Before prompt 5 those two would have sat in a single list beside the three real sources, and a reader would have had no way to tell them apart.

5. A score of five out of five describes the run, not the answer. Every check looks at what the agent did: whether it searched, whether it read more than one page, whether it stayed in budget, whether the brief has a recommendation and at least three sources. None of them asks whether the price is correct, and none could.

6. This evidence goes stale, and that is part of the lesson. A page giving today's price says something different tomorrow. If you want to check a claim in your own brief against its source, do it the same day you run the agent. With a question about current events, the evidence is perishable in a way it is not for a question about how something works.

7. It stopped because it had evidence, not because it had an answer. The model could have written a plausible answer about gold at step one from what it already knew. The rule you add in prompt 5 is what stopped it, and that rule lives in your program rather than in a request to the model.

If your run does not finish

It happens. Running this same question three times gave two complete runs and one that used all eight steps without finishing, because five of the pages it tried that time were refused.

If yours runs out of steps, submit it. A run that shows the agent trying four sites, getting turned away by three, and running out of budget is real evidence about how this work goes. Do not run the program twenty times hoping for a tidier result.

Read your own trace before you submit it

Start by counting two numbers, because they are easier to trust than an impression.

  • How many times does Observation: N chars appear in my run? That is how many pages my agent read.
  • How many entries are listed under Sources:?
  • If those two numbers are different, what explains the difference?

Then read the trace and the brief together.

  • Does any step change because of what the step before it found?
  • Did my agent read any web pages, or did it answer from the search results alone?

  • Did my agent look for anything that might contradict its answer?
  • Would a reader be able to see what my brief does not know?
  • Do my safeguards deal with the risks that my own trace actually shows?
  • If I ran it again right now, would I get the same result? How would I know?

10. If something goes wrong

You are building alone during the week, so read this section before you start. Every problem below has an answer, and none of them costs you marks.

If your build fails completely

Take the checkpoint file, run it on your own question, and do the assignment on that. Write in your your terminal output that you did.

This costs you nothing. What is marked is your reasoning about what the agent did, not whether you got the code working unaided. Do not submit nothing because your code broke.

If your searches stop returning results

Switch on the saved results. In your .env file, set:

USE_FIXTURES=1

The saved results are already in the repository you cloned. Your agent will run normally on them. Note in your terminal output that you used them.

Every call fails, and the error says 403 or 1010

What it means. Every program that asks a website or a service for something also sends a short line saying what kind of program it is. Browsers send one. Python sends one that marks it as a script, and many services refuse scripts before they look at anything else. Your key is fine. Your program never got far enough for the key to matter.

What to do. Prompt 1 asks for a browser-style User-Agent header on every call. If your program does not send one, ask OpenCode Zen to add it.

The run pauses, and the error says 429 or mentions a limit

What it means. You have asked the service too many times too quickly, so it is making you wait. Every step of your agent is one request, so a full run uses several. This is not a fault in your code.

What to do. Nothing. Your program prints how long it is waiting and then tries again by itself. Let it finish rather than pressing Ctrl-C.

If it keeps happening, read the trace you already have instead of running the program again. Most of what you need to know is in it, and running the same code again rarely gives a different answer.

One thing that is not an error. A full run of the finished agent takes roughly a minute and a half, because the model inside your program is slower than the one that writes your code. Long silences are normal. Do not interrupt it.

Everything else

Your code does not run. This is normal. Describe the problem to OpenCode Zen in your own words. If it is still broken after two attempts, click Ask for Help in your team room and take the checkpoint file.

You see 503, or the words "Service Unavailable". The service was busy for a moment, and this has nothing to do with your code. Run the program again. If it happens every time, your program is missing the instruction in prompt 1 to wait a moment and try again. Ask OpenCode Zen to add it.

An error message shows your API key. Delete that key at opencode.ai/auth and create a new one. Then check that your program sends the key in a header and not in the URL, because that is what caused it. Do not paste the error into the chat.

You are behind the rest of the class. Take the checkpoint file for the step you are on and continue with everyone else. The checkpoint files exist for this. Falling behind on the code is not the same as falling behind on the learning, and the thinking is the part that is marked.

Your searches stop returning results. The whole class is searching at the same time, so this will happen to some people. Switch to the saved results your instructor provides. The agent behaves the same way with them.

The text from read_webpage is mostly menus and links. This is normal and it is worth noticing. Websites put a lot of navigation in their pages, and your agent reads it along with the article. Ask yourself what this does to the agent's next decision. It is worth watching for in your own trace.

Your agent runs but you cannot explain what it did. This is the most important problem to raise, and it is not embarrassing. Ask your team to look at your trace with you. Ask what the agent will do next before you run the next step.
